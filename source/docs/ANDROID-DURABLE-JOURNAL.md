# Confirm a device notebook write before saying saved

This private .4 follow-up preserves the .3 freeze a3714a0. No model/dependency/theme changes. The reproduced .3 defect was product-facing: after the editor closed and its success message was displayed, immediately force-stopping the task-owned Android16 ARM64 process lost the journal in all four controlled runs. The host stop completed58–90ms after observing the receipt. The saved entry was present in localStorage immediately before stopping; the cold restart recovered old draft/trip keys and no journal. No post-receipt settling delay was added. The first failed input harness closed the editor with Escape; it is retained separately and is not persistence evidence.

The .3 chain had no asynchronous durable acknowledgement: saveDiscovery → context.commit → localStorage.setItem → in-memory journal update → clear recovery/linked trip → success text. The browser Storage setter updates a storage map; its readback does not confirm disk commit. Chromium's current implementation batches local-storage commits (default5seconds). That is consistent with this timing but does not identify the exact schedule in the tested WebView133.0.6943.137. Android WebStorage provides no public localStorage flush acknowledgement.

The Android .4 chain is: validate current cached bytes and recovery limits → await existing origin-scoped WebMessagePort request → serialized native compare-and-set → AtomicFile.startWrite → write UTF8 snapshot → FileDescriptor.sync → finishWrite → exact-byte openRead → owner-scoped acknowledgement → update WebView cache/state → clear completed recovery/link → success text. There is no fixed settling wait in this chain. All notebook mutations share the guard; browser commits retain their Web Storage behavior. Save controls and Back/discard stay pending while the commit is outstanding. Duplicate submits cannot create a second entry. Backup preview controls/Cancel are held while a started commit settles, so the receipt describes the captured plan.

Before reading or mutating the native file, the same serialization lock checks that the request still belongs to the live Activity and current port. An old executor job queued before Activity destruction cannot resurrect entries after a fresh clear even when both expected revisions are null. The private instrumentation fixture tests this with a latch-held old executor, actual Activity recreation, a new-owner clear, and awaited stale Future/executor termination rather than a settling delay. It calls the production writer with synthetic requests; separate UI runs exercise actual port receipts.

The durable private journal is canonical on Android. A bootstrap reads the bounded same-origin native endpoint before the existing UI reads its WebView cache. Absent native data adopts the existing .3 cache at the first successful write. Exact completed recovery is removed only when ID, normalized text, immutable task snapshot, tags, scene and editing revision match the committed entry; a different trip token or changed unsaved draft stays. Personal-clear awaits removal of the canonical journal; cards, trip and draft copies retain their existing Web Storage durability limit. Its Android receipt explicitly qualifies those other removals; no permanent hash tombstones are retained that could erase newly recreated identical values. Private data remains inside this app's files directory. Existing document actions, model assets and permissions are unchanged.

Native failure, missing connection, timeout or changed expected bytes never produce a save success receipt. A timeout is an uncertain write, not proof of cancellation: a copy may have been written. If native acknowledgement succeeds but WebView caching fails, subsequent writes are locked with an explicit already-written warning and the draft remains until reopening. An unreadable native canonical file is preserved and saving/removal remains blocked; a page raw rescue is only its WebView cache, not a rescue of that unreadable private file. Repairing such a damaged canonical file is outside this focused patch.

This bounds a demonstrated post-success rapid-process-stop defect. It does not promise survival of arbitrary OS/kernel/storage failures, hardware power loss, uninstall, app-data clearing or all future WebViews. Unconfirmed work may complete before the process is killed and must be checked after reopening. Browser offline/cache acceptance remains attributed to its prior version. Final frozen execution reports are outside the source archive in the private review kit; preliminary dirty-build results are labelled separately.
